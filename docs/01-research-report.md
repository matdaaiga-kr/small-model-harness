# 로컬 LLM 하네스 엔지니어링 리서치 보고서

- 작성일: 2026-07-17 (딥리서치 실행: 2026-07-12, 24개 소스 · 120개 주장 추출 · 46건 교차 검증)
- 대상 하드웨어: MacBook Air M2 (Mac14,2) — 8코어 CPU(4P+4E), 10코어 GPU, **16GB 통합 메모리**, 디스크 여유 ~35GB, 팬리스
- 목적: 한국어 Obsidian 위키에 대한 에이전트 하네스(툴 콜링, RAG, ingest/query)를 로컬 LLM으로 구축

---

## 1. 최종 추천

- **모델: Qwen3-8B (Q4_K_M 또는 Q5_K_M, 4.6~5.5GB)**
- **임베딩: KURE-v1** (한국어 특화, MIT) 또는 BGE-M3
- **런타임: Ollama로 시작** → 구조화 출력 제어가 필요하면 llama.cpp server(GBNF), 성능이 필요하면 mlx-lm

## 2. 모델 선정 근거

### Qwen3-8B

- BFCL V4(2026-04-12) 툴 콜링: **42.57% (네이티브 FC)** — Gemma-3-12B 30.43%, Phi-4 28.79%, Llama-3.1-8B 25.83%를 크게 상회.
- **멀티턴(에이전트 루프) 정확도 41.75%** vs Gemma-3 5.75%, Phi-4 3.88%, Llama-3.1-8B 11.12% — 동급 범용 모델 중 압도적.
- 실측 사례: read-then-edit 에이전트 태스크에서 Qwen3-8B 통과, Qwen2.5-14B는 실패 → 툴 콜링은 파라미터 수보다 **모델 세대**가 중요.
- Apache-2.0 라이선스.
- M2 Air 예상 생성 속도: 12~25 tok/s (소스 간 편차, 보수적으로 ~15 tok/s).

## 3. 런타임 비교

| 런타임 | 장점 | 비고 |
|---|---|---|
| **Ollama** | OpenAI 호환 `/v1/chat/completions` + `/v1/embeddings` + tools API, 최저 설정 비용 | v0.19(2026-03)부터 Apple Silicon MLX 엔진 지원(safetensors 라우팅) |
| **llama.cpp server** | GBNF grammar로 JSON 스키마 강제, `--jinja`로 툴 콜링, GGUF 생태계 최광 | grammar와 네이티브 함수콜링은 **동시 사용 불가**(택1) |
| **mlx-lm** | Apple Silicon 디코드 20~40% 우위 보고 다수, OpenAI 호환 서버 내장 | **M2 세대에서는 GGUF와 사실상 동률**이라는 실측 존재(M2 Max: 13.7 vs 14.0 tok/s). 프리필은 오히려 GGUF가 우세한 경우도 |
| LM Studio | GUI 편의 | 하네스 학습 목적에는 불필요한 계층 |

검증에서 드러난 중요 사실 두 가지:

1. arXiv 2511.05502의 "Ollama는 function calling/embeddings 미지원" 주장은 **명백히 오류**
   (Ollama는 2024-07부터 둘 다 지원). 논문의 성능 순위(MLX > llama.cpp > Ollama)는 유효하되 M2 Ultra 기준.
2. "Qwen3+Ollama 툴 콜링은 신뢰할 만하다"는 주장도 Ollama 이슈 트래커의 실제 버그들(#14601 등)로 반박됨.
   → **런타임을 맹신하지 말고 하네스 레벨 검증·재시도를 직접 구현할 것** (= 이 프로젝트의 존재 이유).

## 4. 임베딩 (한국어 RAG)

- **KURE-v1** (고려대 NLP&AI Lab, MIT): BGE-M3를 한국어 200만 쌍으로 파인튜닝. MTEB 한국어 검색에서
  BGE-M3, multilingual-e5-large, OpenAI text-embedding-3-large 모두 능가 (Recall@10 0.797, NDCG 0.695). 1024차원.
- **BGE-M3** (MIT): 8192토큰 컨텍스트, dense+sparse+ColBERT 3중 검색. 다국어 안전빵.
- **EmbeddingGemma-300M**: 양자화 시 200MB 미만 — 메모리 최우선일 때.
- 리랭커: **bge-reranker-v2-m3** (선택적 2단계).

## 5. 16GB 메모리 예산

```
총 16GB (모델 가용 실질 한도 ~11GB)
├─ macOS + 런타임 오버헤드      ~4.5GB
├─ Qwen3-8B Q4_K_M             ~5GB
├─ KV 캐시 (8K ctx, Q8)         ~1-2GB
├─ KURE-v1 (fp16)              ~1.2GB
└─ 여유                         ~2-3GB
```

- 컨텍스트 **8K가 현실적 상한**, 32K는 사실상 불가.
- **툴 콜링 시 KV 캐시는 Q8 이상** (Q4 양자화는 신뢰성 저하 — 메모리 절약 가치 없음).
- 스와핑 발생 시 40 → 2 tok/s로 붕괴 (통합 메모리 초과는 점진적 감속이 아니라 절벽).
- 팬리스 스로틀링: 15~25분 지속 추론 시 15~25% 감속.
- GGUF와 MLX 포맷은 비호환 → 런타임별 모델 복사본 필요. 디스크 35GB 감안해 **한 포맷으로 통일**.

## 6. 현실적 성능 기대치 (냉정한 평가)

- 병목은 생성 속도가 아니라 **프리필**: M2에서 8B 프리필 ~100-200 tok/s → 4K 프롬프트면 첫 토큰까지 20~40초.
- 자유 멀티스텝 에이전트: 5스텝에 **3~5분** + 멀티턴 정확도 41.75% → 일상 도구로는 부적합, 학습/데모용.
- **파이프라인형 RAG QA** (검색→조립→단발 생성, LLM 1~2회): 응답 10~30초 → **실용 가능**.
- 프런티어 모델(Claude 77.47%)과 35%p 격차 = 하네스가 메워야 할 공간이자 이 프로젝트의 학습 재료.

## 7. 하네스 설계 핵심 패턴 (리서치 검증됨)

1. **복리 실패**: 스텝당 성공률 95%도 8스텝이면 E2E 66%. 스텝 수 자체를 줄이는 설계가 최우선.
2. **형식 보장 ≠ 의미 보장**: GBNF/JSON 스키마는 유효한 JSON만 보장. 함수명은 툴 레지스트리와 대조,
   인자는 코드에서 검증 + 재시도 루프. (스키마 오류의 65%는 "환각 키 + 미폐괄호" — grammar가 정확히 막아주는 유형)
3. **스키마는 얕게**: enum/const 우선, 필수 필드 최소화, temperature ~0.
4. **가드레일 한 줄의 힘**: "실패한 툴 콜을 반복하지 마라" 시스템 프롬프트로 무한루프 해소, 토큰 30K→9K 실측.
5. **툴 정의는 개당 50~150토큰**: 8K 컨텍스트에서 툴은 3~4개 이하로.
6. **엄격한 형식 강제는 추론력을 깎을 수 있음** (수학 벤치마크 최대 -27%p) — 추론 단계와 출력 단계 분리 고려.
7. 청킹: 헤딩(H2/H3) 단위, 한국어는 300~400토큰(영어 500+보다 작게), 오버랩 15%. 형태소 분석(Kiwi) 전처리가 검색 품질 향상.
