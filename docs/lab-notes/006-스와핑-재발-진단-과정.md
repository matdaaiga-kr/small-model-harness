# 006 — 스와핑 재발: 진단 과정 전체 기록

날짜: 2026-07-19 · 상황: M4 재실험 +evidence 설정 실행 중 · 관련: [002](002-스와핑-절벽-mps-캐시.md), [005](005-m4-개입은-실패를-재배치한다.md)

M2 때의 스와핑 절벽(002)이 M4에서 다른 경로로 재발했다. 이번에는 "무엇을
보고 스와핑이라고 결론지었나"의 진단 체인 자체를 명령·출력과 함께 남긴다.

## 상황

M4 재실험(72런) 중 +evidence 설정 구간에서 완료 감지 모니터가 60분
타임아웃했다. 직전까지 런당 60~90초였는데 30분 넘게 진행 표시가 없었다.
가능성은 셋: ① 프로세스 사망 ② 행(hang) ③ 극단적으로 느려짐.

## 진단 체인: 명령과 출력

### 1단계 — 죽었나? (사망 배제)

```bash
$ pgrep -fl "harness eval ablation"
5526 uv run harness eval ablation --exp m4-planner
$ curl -s -m 5 http://localhost:11434/api/ps
{"models":[{"name":"qwen3:8b", ...}]}          # Ollama도 생존, 모델 로드 상태
```

프로세스와 추론 서버 모두 살아 있다. ① 배제.

### 2단계 — 멈췄나? (행 배제)

```bash
$ stat -f "출력 마지막 수정: %Sm" tasks/….output
출력 마지막 수정: Jul 19 12:39:47 2026          # 4분 전 — 갱신은 되고 있다
$ ls -lt traces/runs/ | head -4
12:42  r_20260719_1239_….jsonl                  # 진행 중인 런
12:39  r_20260719_1234_….jsonl                  # 직전 런: 12:34 시작 → 12:39 종료
12:34  r_20260719_1230_….jsonl                  # 그 전 런: 12:30 → 12:34
```

트레이스 파일이 4~5분 간격으로 계속 생성되고 있다 → 행이 아니라 **런당
60~90초 → 4~5분으로 느려진 것**. ② 배제, ③ 확정. 이제 "왜 느린가".

### 3단계 — 어디가 느린가? (트레이스로 병목 위치 특정)

런 트레이스에서 LLM 호출 이벤트만 추출:

```
r_20260719_1234: step 1 →   9,715ms
                 step 5 → 109,677ms   ← 툴 결과 주입 후 첫 호출
                 step 7 →  29,352ms
                 step11 → 135,159ms   ← 반려 후 재답변 호출
```

평소 10~30초인 LLM 호출이 **100~135초**. 같은 이벤트에 기록된 생성 속도는
`tok_per_s: 4.4` — 정상(수십 tok/s) 대비 10배 이상 붕괴. 병목은 검색도
파이썬도 아닌 **추론 자체**다. 프롬프트가 길어진 것도 아니다(1.3k 토큰).
"프롬프트는 그대로인데 추론만 10배 느림" = 연산이 아니라 메모리 대역 문제를
시사한다.

### 4단계 — 시스템 메모리 상태 (스와핑 확증)

```bash
$ sysctl vm.swapusage
vm.swapusage: total = 7168.00M  used = 5910.56M  free = 1257.44M
$ vm_stat | head -5
Pages free:  4430.        # × 16KB ≈ 여유 램 70MB
Pages active: 111719.
```

스왑 7GB 중 **5.9GB 사용**, 물리 램 여유 **~70MB**. 스와핑이 일어나고
있다는 직접 증거. 남은 질문은 "누가 누구를 밀어내나".

### 5단계 — 범인 식별 (점유 순위와 결정적 단서)

```bash
$ ps axo rss,pid,comm | sort -rn | head
5932MB  llama-server        # Ollama 추론 엔진 — 모델 가중치+KV캐시
 305MB  claude
 163MB  Claude.app / 102MB Discord / 64MB Chrome ...
  64MB  Python (실험 프로세스)   ← 결정적 단서
```

**파이썬 프로세스 RSS 64MB가 결정적 단서다.** 이 프로세스는 KURE-v1 임베더
(sentence-transformers, 로드 시 2GB+)를 들고 있다. RSS가 64MB라는 것은
임베더가 **통째로 스왑에 밀려나 있다**는 뜻이다. 트레이스의 mem 스냅샷도
일치한다: `"mem": {"rss_mb": 55, "avail_mb": 1732}` — 실험 프로세스 자신이
55MB까지 짜부라져 있다.

## 결론

**메커니즘 — 임베더⇄추론엔진 핑퐁 스래싱:**

```
16GB 통합 메모리 = llama-server 5.9GB + 임베더 2GB+ + 시스템/앱 → 초과
+evidence 런: search_wiki 호출(런당 3회+)
  → 임베더를 스왑에서 페이지-인 → llama-server 페이지가 밀려남
  → 다음 LLM 호출에서 llama-server를 다시 페이지-인 → 호출당 100초+
  → 다시 search_wiki … (반복)
```

control/+planner(런당 툴콜 0~1회)에서는 왕복이 드물어 안 터졌고,
+evidence(반려 → 추가 검색·읽기 강제)가 정확히 이 왕복을 최대화했다.
**개입의 런타임 비용이 하네스 계층이 아니라 메모리 계층에서 발생**한 사례.

002와의 차이: 002는 임베더의 MPS 캐시 미해제가 원인(코드 수정으로 해결),
이번엔 워크로드 자체가 두 대형 프로세스를 번갈아 깨우는 구조라 **코드로
제거 불가** — 완주를 선택하고 개입하지 않았다 (진행 중 실험의 조건을
바꾸면 데이터가 오염된다).

**판단 원칙으로 일반화:**

1. 사망/행/저속은 서로 다른 문제다 — 프로세스 생존(pgrep), 산출물 갱신
   (mtime/트레이스), 병목 위치(트레이스 레이턴시) 순으로 배제한다.
2. "프롬프트 불변인데 추론만 수 배 느림 + tok/s 붕괴"는 메모리 압박의
   시그니처다. `sysctl vm.swapusage`와 `vm_stat`으로 즉시 확증할 수 있다.
3. 큰 모델을 든 프로세스의 **RSS가 비정상적으로 작으면** 그 프로세스는
   스왑에 밀려나 있는 것이다. `ps axo rss`는 "지금 램에 있는 양"만 보여준다.
4. 트레이스에 mem 스냅샷을 남겨둔 것(`harness/obs/trace.py`)이 사후 진단을
   가능하게 했다 — 계측은 문제가 생기기 전에 심어야 한다.

## 영향

- 16GB에서 검색(임베더)과 생성(LLM)을 오가는 워크로드는 설계 단계에서 스왑
  왕복 횟수를 비용으로 계상할 것.
- 실험 프로세스가 이 압박으로 2회 사망 → `--resume`(005)으로 대응 완료.
- 근본 완화 후보: 임베딩을 사전 계산·캐시해 실험 중 임베더 로드를 없애기,
  또는 BM25-only 검색 모드(단, 검색 품질 조건이 바뀌므로 별도 실험으로).
