# 003. 툴콜 유효율 null result — M4 가설을 "탐색 소극성 공략"으로 전환

- 날짜: 2026-07-18 / 마일스톤: M3 / 커밋: 14839f7 / 상세: reports/ablation-m3-2026-07-18.md

## 상황

M3의 핵심 실험 — baseline → +validator → +retry → full 순차 도입으로 툴콜 유효율의
계단식 상승을 측정 — 을 두 차례 실행.

## 증거

- 1차(단일홉 8태스크 × 4설정 = 32런): 전 설정 이름/인자 유효율 100%, 성공률 100% 동률.
- 2차(멀티홉 3 + 함정 3 추가, 10태스크 × 4설정 = 40런): 여전히 유효율 100%.
  Validator·RetryLoop·Guardrails 발동 **0회**. 함정(쓰기 요구, URL 요구)에서도 툴 환각 없이
  거절, 부재 주제도 반복 루프 없이 1회 검색 후 종료.
- 유일한 실패: q-101(두 프로젝트 인증 비교)이 4/4 설정에서 동일하게 실패 — 검색 1회 후
  스니펫만으로 조기 답변, 두 번째 페이지를 read_page로 확인 안 함. 평균 스텝 1.9/상한 6.

## 해석

1. BFCL 멀티턴 41.75%는 수십 개 툴·깊은 스키마·상태 추적 조건의 숫자. **툴 3개·문자열
   인자 1~2개·temp 0.2**에서는 실패 자체가 일어나지 않는다. 리서치 §7-3("스키마는 얕게")을
   설계에 반영한 것이 실패를 설계로 제거함.
2. 하네스 모듈은 이 툴 표면에서 "발동 0회의 보험" — 폐기가 아니라 유지(지연 비용 0,
   툴 확장 시 발동 예상). 단, 이 축의 추가 측정은 정보량이 없다.
3. 실제 병목은 유효율이 아니라 **탐색 소극성(조기 답변)**: 모델이 스텝 예산을 남기고도
   불충분한 근거로 답을 완성한다.

## 결정

M4의 A/B 가설을 변경한다:
- (폐기) "검증/수리/가드레일 도입이 유효율·성공률을 올린다" — 72런으로 반증됨.
- (신규) "멀티홉 계획 강제 — 질문의 각 대상마다 검색·읽기 후 답변하게 하는 개입(프롬프트
  한 줄 vs 루프 레벨 근거 검사) — 가 E2E 성공률을 올린다"를 측정. 비용(스텝·토큰 증가)도
  함께 기록.
- 기존 4설정은 3회 반복으로 null result의 분산만 확인하고 종료.

## 영향

- 로드맵 M4 내용 변경 (docs/02 §6의 "A/B 러너, 하네스 개입 효과 보고서" 취지는 동일,
  측정 대상 개입이 바뀜).
- 태스크 스위트에 kind(qa/probe)·require_all 채점 축 추가됨 — 이후 스위트 확장 시
  멀티홉 태스크를 늘릴 것 (현재 3개는 표본이 얇다).
- 교훈: 어블레이션은 "실패가 존재하는 구간"에서만 정보를 준다. 실험 설계 전에 베이스라인의
  실패율부터 확인할 것.
