# 004. 채점기 오염 — M4 1차 결과(개입이 해롭다) 무효 판정

- 날짜: 2026-07-18 / 마일스톤: M4 / 관련: lab-notes/003, reports/ablation-m4-planner-2026-07-18.md (무효)

## 상황

m4-planner 1차 실험(3설정 × 8멀티홉 × 3반복 = 72런) 결과가 control 67% > +planner 62% >
+evidence 42%로 "개입이 성능을 깎는다"로 나옴. 태스크별로 뜯어보니 채점 자체가 오염.

## 증거

- q-111 (+evidence 0/3, control 3/3): 실패 답변이 페이지명을 `코멘토-GAS-교육효과-대시보드`
  (대문자)로 표기 — 실제 페이지명은 `코멘토-gas-…`(소문자). 채점이 **대소문자 구분 substring**
  이라 내용상 정답을 오답 처리.
- 같은 이유로 `read_page`(정확 키 조회)도 대문자 이름을 거부 → evidence 반려 후 재읽기가
  실패하며 스텝 소진 → 폴백 증가 (q-103#r2 스텝 6 폴백).
- q-103 (+planner 0/3): 답변이 contact 캡스톤 알림을 `프로젝트-contact-캡스톤` 등 **동의
  페이지**로 인용 — 기대 페이지 `sse-eventsource-실시간-알림`만 정답으로 인정돼 탈락.
  위키는 같은 주제를 여러 페이지가 다루므로 단일 정답 페이지 강제는 과도.
- 대조: 개입 없는 control은 검색 스니펫의 표기를 그대로 베끼는 경향이라 우연히 대소문자가
  일치 — **개입 설정만 체계적으로 불리한 편향**이 생김.

## 해석

측정계의 두 결함(대소문자 구분, 동의 페이지 미인정)이 개입 설정에 비대칭으로 작용해
1차 결과의 부호 자체를 신뢰할 수 없음. "개입이 해롭다"는 결론은 무효. 단, 부수 관찰은 유효:
evidence 개입의 스텝 비용(1.9→5.0)과 read_page 대소문자 취약성은 실제 문제.

## 결정

1. 채점: casefold 비교로 변경, 멀티홉은 `page_groups`(홉마다 동의 페이지 목록 중 1개) 도입.
2. `read_page`: 대소문자 무시 조회 + 실읽기 추적도 casefold.
3. metrics.sqlite에 최종 답변 원문을 저장 — 이후 채점기 수정 시 재채점 가능하게 (이번에
   재실험이 필요해진 근본 원인이 답변 미보존).
4. m4-planner 전체 재실험.

## 영향

- reports/ablation-m4-planner-2026-07-18.md는 무효 표기 유지(삭제하지 않음 — 실수도 기록).
- 교훈: 채점기는 피험자보다 먼저 검증할 것. 결정적 채점기도 대소문자·표기 변형·동의 표현
  같은 "정답의 표면형 다양성"을 고려해야 한다.
