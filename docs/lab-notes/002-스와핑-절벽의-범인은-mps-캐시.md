# 002. 스와핑 절벽의 범인은 MPS 캐시 — empty_cache() 한 줄로 p50 46s→9s

- 날짜: 2026-07-18 / 마일스톤: M2 / 커밋: 8d79e0f

## 상황

E2E 평가에서 지연이 태스크를 거듭할수록 21s → 62s → 78s로 붕괴. 같은 크기 프롬프트(~1.9K
토큰)인데 프리필이 105 tok/s에서 25 tok/s로 떨어짐.

## 증거

- trace `r_20260718_1208_4040`: 가용 메모리가 런 시작 5.1GB → 3번째 태스크에 1.0GB로 붕괴,
  평가 프로세스 RSS 854MB → 56MB (스왑아웃). 리서치 §5가 경고한 "스와핑 절벽" 패턴 그대로.
- 수정 후 trace `r_20260718_1216_3309`: 가용 ~2GB에서 안정, LLM 호출 7.5~8.4s로 일정.
  p50 46.0s → **9.0s**, max 78.1s → 23.1s.

## 해석

KURE(PyTorch MPS)가 임베딩 후에도 캐시 버퍼를 쥔 채로 있어, Ollama(GPU 6GB)와 통합 메모리를
경합. 프리필 시 Ollama의 임시 컴퓨트 버퍼(~2GB) 할당이 스왑을 유발. 문서의 메모리 예산(§5)은
"다른 앱이 없는 깨끗한 머신" 가정이라 실사용 환경에선 여유가 더 얇다.

## 결정

1. `embedder.embed()` 직후 `torch.mps.empty_cache()` 호출 (harness/model/embedder.py).
2. PREFILL_BUDGET 3000 → 1500: 실측 프리필(건강 상태 ~105 tok/s, 문서 낙관치 100~200의
   하한)에 맞춰 30초 응답 목표를 지키는 값으로.

## 영향

- M2 완료 기준(응답 ≤30s) 충족 가능해짐.
- 트레이스에 mem 스냅샷을 넣어둔 것이 원인 규명의 결정타 — "모든 호출을 계측" 원칙의 첫 밥값.
- 남은 리스크: 사용자가 무거운 앱을 띄우면 여전히 절벽 근처. 벤치마크 런은 여유 메모리
  4GB+ 상태에서 돌릴 것.
